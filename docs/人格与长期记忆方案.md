# 人格设定与长期记忆方案

> 目标：在**不加依赖、不改存储格式的兼容性**前提下，把现有的「一个人设文件 + 一堆事实字符串」
> 升级成「可分层、可按群、可演化」的两套系统。
>
> 本文是设计文档，不含实现。分期见第六节。
>
> **参考实现**（两个方向相反的项目，各借一半）：
>
> 1. [astrbot_plugin_livingmemory](https://github.com/lxfight-s-Astrbot-Plugins/astrbot_plugin_livingmemory)
>    （AstrBot 长期记忆插件，v2.8.2，AGPL-3.0）：向量 + 全文 + 图谱三路检索、五态生命周期，
>    工业级方案。抄它的**生命周期机制**，不抄它的**技术栈**。
>    最重要的一条调整：**用「类型化 TTL」替代原计划的 episodes 分层**，第二阶段风险降低一档。
> 2. [st-memory-enhancement](https://github.com/muyoou/st-memory-enhancement)
>    （SillyTavern 表格记忆插件，v2.2.19，1081 行 JS，**无许可证**）：用户定义表格 schema，
>    模型只填行，全量注入不做检索。抄它的**schema 约束思路**，不抄它的存储方式。
>    最重要的一条调整：**记忆契约要给「记哪几类」的锚点，而不是只说「记重要的事」**。
>
> 详细的机制拆解与取舍见 `docs/st-memory-可借鉴点分析.md` 与本文第九节。
> 两个项目都只借思路，不借代码（第二个无许可证，更要小心）。

## 一、现状盘点

### 已经有的

| 能力 | 实现 | 位置 |
|---|---|---|
| 人设文件 | `presets/<id>.yaml`，字段 `name` / `system` / `temperature` / `maxTokens` / `recallSeconds` / `enabled` | `models/preset.js:24` |
| 人设选择 | 关键词规则 > 默认 ID > 内置兜底 | `models/preset.js:95` `resolvePreset()` |
| 统一前缀 | `speaking.presetPrefix` 拼在每个人设前面 | `models/chatService.js:25` |
| 记忆存储 | `data/memory.json` → `groups[群号].facts[]` | `models/memory.js` |
| 记忆产出 | 回复副产品（`{say, memory}` 契约） | `models/replyParser.js` |
| 记忆检索 | 2-gram 相似度 0.6 + importance 0.25 + 时效 0.15 | `models/memory.js:104` |
| 记忆上限 | 每群 200 条，超了淘汰「最不重要且最旧」 | `models/memory.js:167` |

### 缺的口子

**人设侧：**

1. **只有一整段 `system` 文本。** 想改「口癖」得重写整段 prompt，改错一个字整段就废了。
2. **人设绑不到群。** `resolvePreset(text)` 只接收消息文本，拿不到 `groupId`。
   现在的效果是「同一个机器人，在所有群里是同一个人」——想给 A 群配高冷、B 群配沙雕做不到。
3. **没有运行时切换。** 换人设要改 yaml + 等 5 秒缓存过期（或 `#bym 重载`），
   而且改的是全局默认值，不是「就这个群」。
4. **`presetPrefix` 是全局的。** 一旦填了，所有群都套同一句开头。

**记忆侧：**

1. **只记事实，不记人。** `"张三在字节跳动做后端"` 是一个不可解析的字符串。
   想知道「张三」相关的所有事情，只能靠 2-gram 碰运气。
2. **无冲突消解。** 群里先说「张三在字节」，两个月后说「张三跳槽去腾讯了」，
   两条都会留在库里，注入时可能**同时出现**，模型只能瞎猜哪个是真的。
3. **单层，无轻重。** 群的性质（「这是个游戏群」）和一次性事件（「上周六爬山」）
   平铺在同一个数组里，靠 `importance` 一个数字区分。前者本该每轮都注入，后者一周后就该淡出。
4. **没有相关性门槛 —— 这是实测出来的最严重一条。** 见下。
5. **满了就丢。** 200 条上限后按分数淘汰，没有压缩。半年前的群约定和昨天的闲聊被同等对待。

### 关于「相关性」的实测数据

用真实的 `memory.js` 跑了一遍（3 条记忆，模拟查询）：

| 查询 | 张三在字节做后端<br>rel / 总分 | 李四养了两只猫<br>rel / 总分 | 周六爬山<br>rel / 总分 |
|---|---|---|---|
| 谁养猫 | 0.000 / **0.350** | 0.000 / 0.275 | 0.000 / 0.250 |
| 周六干什么 | 0.000 / **0.350** | 0.000 / 0.275 | 0.167 / 0.350 |
| 张三在哪工作 | 0.270 / **0.512** | 0.000 / 0.275 | 0.000 / 0.250 |
| 今天好热 | 0.000 / **0.350** | 0.000 / 0.275 | 0.000 / 0.250 |

三件事：

1. **「谁养猫」的相关度是 0。** 因为记忆原文是「李四**养了两只猫**」，
   而 2-gram 里没有「养猫」这两个连续的字。**跨词的语义关联，2-gram 天生抓不到。**
2. **相关度 0 的条目照样被注入。** 打分公式里 `importance*0.25 + freshness*0.15 = 0.4`，
   一个完全无关但重要的记忆能拿 0.35 分，稳定进入 top N。查询「今天好热」时，
   模型会收到「张三在字节跳动做后端」——它很可能就把这句写进回复里。
3. **相关条目和无关条目同分。** 「周六干什么」时，"周六爬山"（rel 0.167）和"张三在字节"（rel 0）
   总分都是 0.350，谁排前面取决于排序稳定性。

**结论：问题不是「2-gram 太弱」，而是「没有门槛，无关条目也会被塞进 prompt」。**
这个修复只要一行（`relevance > 0` 才注入），收益却是最大的一条 ——
它决定模型是「用对了记忆」还是「拿着一条无关记忆瞎发挥」。
所以它被单独提到一期，优先级最高。

## 二、人设方案

### 2.1 结构化人设（向后兼容）

`presets/*.yaml` 保留 `system` 字段不变（老文件照常工作），新增**可选**的结构化字段。
`buildSystemPrompt()` 的规则：**有结构化字段就按模板生成段落，没有就用 `system` 原文**。

```yaml
# presets/bym_default.yaml —— 新版示例
id: bym_default
name: 小张

# 可选：结构化身份。给了这些就不需要 system 里再描述一遍
identity:
  age: 24
  city: 杭州
  job: 后端开发
  signature: 常年加班，爱喝冰美式

speech:
  style: 口语、简短、偶尔阴阳怪气
  length: 一到两句          # 一句话的长度约束，比 system 里写"简短"更明确
  catchphrases: ['确实', '行吧', '有点离谱']
  never: ['不说脏话', '不发长段', '不用敬语']

# 可选：保留自由文本，作为补充或完全替代结构化字段
system: |
  你不太主动，但被问到会认真答。

temperature: 0.9
maxTokens: 200
```

**为什么值得做**：改口癖只改一行 `catchphrases`，不用碰整段 prompt；
换人设可以只换 `identity` 而复用同一套 `speech`。

**坑**：结构化字段容易写得太细（把 prompt 塞进 yaml），最后比原来更难维护。
所以字段只放**必须程序化处理**的东西（长度约束、口癖列表、禁忌），
其余表达留给 `system`。

### 2.2 群级人设绑定

新增配置：

```yaml
speaking:
  groupPresets:           # 群号 -> 人设 ID
    '123456789': bym_tsundere
    '987654321': bym_default
```

`resolvePreset()` 签名改为 `resolvePreset(text, groupId)`，优先级：

```
群绑定 > 关键词规则 > 默认 ID > 内置兜底
```

**为什么群绑定优先级最高**：关键词规则是「聊到原神就换成原神人设」，
这是**话题级**的临时切换；群绑定是「这个群就用这个人」，是**场地级**的设定。
场地比话题更根本 —— 在「原神群」里聊到加班，不该变成通用群友。

**兼容性**：`groupPresets` 为空时行为与现在完全一致。

### 2.3 运行时切换

新增管理指令（均为 master 权限）：

| 指令 | 作用 | 写入位置 |
|---|---|---|
| `#bym 人设` | 列出所有人设，标出当前群在用的那个 | — |
| `#bym 人设 <id>` | 本群切到该人设 | `speaking.groupPresets[本群]` |
| `#bym 人设 off` | 取消本群绑定，回到全局默认 | 从 `groupPresets` 删除 |
| `#bym 人设 预览 <id>` | 用该人设试说一句（不发送） | — |

**为什么不是 `#bym 人设` 直接改 `defaultPresetId`**：那会改掉所有群。
在 A 群调成沙雕人设，B 群的严肃场景就毁了。所以一定要写群级配置。

### 2.4 prompt 拼装变化

现在（`buildSystemPrompt`）：

```
[presetPrefix] + [preset.system] + [固定约束]
```

改成（结构化字段存在时）：

```
[presetPrefix]
# 你是谁
你是{name}，{age}岁，在{city}做{job}。{signature}

# 你怎么说话
{speech.style}。每次说{length}。
偶尔用这些口头禅：{catchphrases.join('、')}。
绝对不要：{never.join('、')}。

# 你在哪
这里是 QQ 群「{群名}」。你是群里的普通成员，不是助手。

[preset.system（若存在）]
[固定约束]
```

**新增 groupName**：`buildSystemPrompt` 需要群名参数。
现在 prompt 里从来没告诉模型「你在哪个群」，这也是它在不同群里说话一个味的原因之一。

## 三、记忆方案

### 3.1 两层 + 类型化 TTL

`groups[群号]` 从 `{ facts: [] }` 扩展为：

```json
{
  "profile": {
    "about": "游戏群，主要聊原神和日常，氛围轻松",
    "updatedAt": 1730000000
  },
  "facts": [ /* 现有结构 + type / expiresAt / accessCount */ ]
}
```

| 层 | 内容 | 生命周期 | 注入策略 |
|---|---|---|---|
| `profile` | 群的性质、长期氛围、固定成员 | 永久，手动或低频更新 | **每轮都注入**，控制在 100 字内 |
| `facts` | 成员身份、群约定、事件 | 按 `type` 决定 TTL（见下） | 按相关度取 top N |

**为什么 profile 要单独一层**：现在的 `facts` 里最稳定、最该一直记着的东西（「这是个游戏群」）
和一次性事件混在一起，靠 2-gram 去碰。而「这是个什么群」几乎每轮都有用，
不该参与相关度竞争 —— 它是**背景**，不是**检索结果**。

**为什么不再单独设 episodes 层**：这是参考 LivingMemory 之后改的。

原本打算新开一个 `episodes` 数组存近期事件，30 天后衰减。但 LivingMemory 的做法更省：
**给每条记忆一个类型，按类型定过期时间**，过期就不参与检索 —— 不需要新的数组、新的层级、
新的注入段落，只要在每个 fact 上加两个字段。

```json
{ "type": "event",  "expiresAt": 1730600000 }   // 事件，7 天后自动不检索
{ "type": "fact",   "expiresAt": 1745500000 }   // 长期事实，180 天
```

| 类型 | TTL | 例子 |
|---|---|---|
| `plan` | 2 天 | 「明天下午三点开会」 |
| `event` | 7 天 | 「上周六去爬山了，去了 5 个人」 |
| `preference` | 60 天 | 「群主不喜欢有人发语音」 |
| `relation` | 90 天 | 「老王是老李的同事」 |
| `fact` | 180 天 | 「张三在字节做后端」 |
| `unknown` | 30 天 | 模型没给出类型时的兜底 |

**收益**：二期的改动从「新增数据库结构 + 改注入格式」降为「加三个字段 + 一个过滤条件」。
数据格式变化极小，老数据全部能继续用（缺 `type` 的按 `unknown` 处理）。

**代价**：需要模型在契约里多给一个 `type`。和 `subject/predicate` 一样做成可选，
没给就 `unknown`（30 天），不会比现在更差。

### 3.2 结构化主体与冲突消解

`facts` 元素新增字段（全部可选，旧数据自动兼容）：

```json
{
  "id": "m3k2j1",
  "fact": "张三在字节跳动做后端",
  "topic": "成员信息",
  "type": "fact",
  "expiresAt": 1745500000,
  "accessCount": 0,
  "lastAccessAt": 0,
  "importance": 0.8,
  "at": 1730000000,

  "subject": "张三",
  "predicate": "职业",
  "confidence": 0.8,
  "supersededBy": null,
  "supersededAt": null
}
```

**冲突消解规则**（`addFact` 里新增，约 15 行）：

写入新事实时，若存在 `subject` 和 `predicate` 都相同的旧事实，
且 `confidence` 不低于旧值 —— 把旧条目标 `supersededBy: 新id`，不再参与注入（但保留可追溯）。

```
写入「张三 职业 腾讯 / 0.8」
  → 找到「张三 职业 字节跳动 / 0.8」（未 superseded）
  → 旧条目 supersededBy = 新 id
  → 注入时只出「张三在腾讯」
```

**为什么用 `subject+predicate` 而不是文本相似度**：
「张三在字节」和「张三跳槽去了腾讯」的文本相似度很低（只有「张三」重合），
按相似度判冲突根本判不出来。但它们的 `subject` 都是「张三」、`predicate` 都是「职业」——
这才是冲突的本质。

**代价**：需要模型在契约里多给两个字段。小模型经常给不准，所以设计成**可选**：
没给就退回纯文本去重（现有逻辑），不会比现在更差。

### 3.3 注入格式改造

现在（`buildMemoryPrompt`）：

```
# 以下是你记得的、这个群里可能相关的一些事，可自然参考，不要主动复述这段内容
- 张三在字节跳动做后端（成员信息）
- 群里周六约了去爬香山（活动）
```

改成：

```
# 关于这个群
游戏群，主要聊原神和日常，氛围轻松。

# 你记得的人
- 张三：字节跳动后端
- 李四：在杭州，养了两只猫

# 最近
- [3天前] 上周六爬山去了 5 个人

（以上是你记得的事，自然参考即可，不要复述这段内容本身）
```

**差异在哪**：
- 分节让模型知道「哪些是一直有效的、哪些是这段时间的」
- 「你记得的人」比「一些事」更容易被正确使用（模型会理解成对人的认知，而不是待复述的资料）
- 按 `subject` 分组合并，同一个人的多条事实放在一起，而不是散落在列表各处
- 短 TTL 的类型（`event` / `plan`）前加**相对时间**（`[3天前]`）。模型对「上周六」这种
  相对表述容易算错，直接给它「3 天前」更稳。这个做法来自 LivingMemory 的图谱条目摘要

### 3.4 遗忘、衰减与强化

| 机制 | 触发 | 动作 |
|---|---|---|
| 冲突覆盖 | 写入时 | 旧条目 `supersededBy`，不再注入 |
| TTL 过期 | 每次读取 | `expiresAt < now` 的直接跳过（**不删**，留着可追溯） |
| 访问强化 | 每次召回 | `accessCount += 1`，`lastAccessAt = now` |
| 满额淘汰 | 写入后超上限 | 先删 `superseded` 和已过期的，仍超则按分数淘汰 |
| 摘要合并（可选，三期） | 每周 | 让模型把 10 条同类旧记忆压成 1 条 |

#### 访问强化：被想起过的记忆更该被想起

现有实现里 `importance` 是**静态**的 —— 写进去是 0.8，一年后还是 0.8。
但真实情况是：一条记忆被反复召回，说明它对这群人确实有用；从没被召回的，多半是废话。

LivingMemory 的做法（架构文档第四节）：**访问降低有效衰减率**，并且
**每次衰减后访问次数 × 0.5**。最后这条很关键 —— 不这么做的话，
一条早期被偶然点开过几十次的旧记忆会永久占据榜首，再也挤不下去。

我们照搬机制，公式自己定（我们的数据量不需要那么精细）：

```js
// 写入时
{ importance: 0.8, accessCount: 0, lastAccessAt: 0, at: now }

// 召回时（在 queryFacts 里）
item.accessCount += 1
item.lastAccessAt = now

// 打分时
const reinforce = Math.min(0.3, accessCount * 0.02)   // 最多 +0.3
const effImportance = Math.min(1, importance + reinforce)
// 同时：距上次访问越久，强化越弱（跟「衰减后 × 0.5」同样的意思）
```

**注意：召回是高频事件，不能每次 `flush()`。** 沿用现有的 `deferred` + `flushMemory()`，
按 3 秒窗口合并写盘（LivingMemory 也是这么做的）。否则每被召回一次就写一次整个
`memory.json`，几十个群跑几天就能把磁盘写满。

**为什么不直接照搬「每日衰减 importance」**：那需要一个每日定时任务。
我们的量级下，「衰减」和「按访问次数加权」在排序上的效果几乎一样，
后者是纯计算、无副作用、不用调度。少一个后台任务就少一个失效点。

### 3.5 契约要给「记哪几类」的锚点

这是参考 st-memory-enhancement 之后加的，**不需要改数据模型，只改 prompt**。

现在 `models/replyParser.js` 的契约是：

```
- memory 只放「以后还用得上」的信息：成员的身份/职业/所在地、群里的约定与梗、发生过的事件。
  寒暄、当下的情绪、你刚说的玩笑话，都不要放。没有就写 []。
```

看着挺具体，但**「值得长期记住的事」本质上是个开放问题**。模型对"什么算重要"的判断
和人不一致，结果就是记一堆「今天天气不错」。

那个表格插件的答案是：**别问开放问题，给结构**。用户先定义列（姓名/身份/关系），
模型只能往里填 —— 它没有跑偏的空间。

我们不用真的建表（群聊里没人愿意维护），但可以借这个思路：**把「记什么」变成多选题而不是问答题**。

```
- memory 优先记这几类（对上号才记，不对号就不记）：
  · 成员的身份、职业、所在地
  · 群里的约定、规矩、固定活动
  · 发生过的事件（带上时间）
  · 某人明确表达过的偏好或忌讳
- 寒暄、天气、当下的情绪、你刚说的玩笑话，都不要记。没有就写 []。
```

**差异**：从一句抽象的「值得长期记住」变成四个可以对照的锚点。
字数只多两行，但模型有了判断依据。

**为什么只给建议、不给强制枚举**：硬性规定「只能记这四类」会漏掉真实存在但没预料到的信息
（比如群里有人的猫叫什么）。锚点是降低跑偏概率，不是画牢。

**成本**：契约从 243 字涨到约 320 字，占 `context.maxChars`（8000）的 4%。
划算。

## 四、数据模型与迁移

### 存储变化

`data/memory.json`：

```json
{
  "version": 2,
  "groups": {
    "123456": {
      "profile": { "about": "", "updatedAt": 0 },
      "facts": [ /* 旧元素缺 type/expiresAt/accessCount，读取时按 unknown / 0 处理 */ ]
    }
  }
}
```

### 迁移策略

**不做显式迁移脚本。** 在 `ensureLoaded()` 里做**读时补齐**：

- 缺 `version` → 视为 1，补成 2
- 缺 `profile` → 补 `{ about: '', updatedAt: 0 }`
- `facts` 元素缺 `type` → 按 `unknown`（30 天 TTL）处理，`expiresAt` 由 `at + TTL` 现算
- `facts` 元素缺 `accessCount` → 当作 0
- 以上补齐**只存在内存**，不立刻写回（避免启动时全量重写一遍几 MB 的文件）

下次有写入时自然落盘成新格式。旧文件直接能用；新文件被旧版本读到也不炸（多个字段而已）。

### 为什么不用 SQLite

现在 `memory.json` 在 200 条 × 几十个群时约几百 KB，全量读写完全够用。
换 SQLite 会引入原生依赖（项目明确的红线），而收益要到「每群上万条」才体现。
真要走到那一步，`queryFacts()` 是唯一的查询入口，换实现不影响上层。

LivingMemory 用的是 SQLite + FTS5 + FAISS 三件套，它的量级是「万节点 + 向量索引重建」，
和我们的场景不是一回事。第九节有完整对比。

| **二期** | 结构化人设字段 + `profile` 层 + 类型化 TTL + 访问强化 | ✅ 1.4.0 | D 期 |
| **三期** | 结构化 `subject/predicate` 抽取 + 摘要合并 + 画像自动维护 | 未做 | 依赖模型输出质量，需要真实数据 |

**实施中修正了两个设计**：

1. **`diversify`（简化版 MMR）删掉了**。原计划用 2-gram Jaccard 合并「换个说法的同一件事」，
   实测发现它和「同主体不同方面」的相似度区间完全重叠（0.08~0.40 vs 0.07~0.43）。
   阈值定 0.7 永不触发，定到能触发的区间就会把「张三在字节」和「张三在腾讯」并成一条。
   这类判断要靠 embedding，而我们不引依赖。真正接近这个问题的冲突消解由 `subject` + `predicate` 解决。
2. **`subject` 必须参与检索**。模型常写成 `{fact: "在字节做后端开发", subject: "张三"}`，
   正文里没有「张三」二字。只看 `fact` 的话，查「张三」时相关度为 0 直接被门槛挡掉，
   而注入时它又该归到「你记得的人 · 张三」那一节 —— 结果就是分节分好了，那一节永远空。
   改成用 `subject + fact` 一起做匹配。

### 第 0 期的最小改动

`models/memory.js` 的 `queryFacts()`，在 `map` 之后加过滤：

```js
const scored = bucket.facts.map(...)
  .filter(item => item.relevance > threshold)   // ← 新增，threshold 默认 0
```

要注意两点：

- **threshold 不能设太高**。2-gram 的 rel 普遍偏低（实测「张三在哪工作」对最相关条目也只有 0.270），
  阈值超过 0.1 会误杀真实相关的记忆。默认 `0`（即「至少有一个 2-gram 重合」）就够，
  因为 rel 恰好为 0 的正是那些完全无关的。
- **`importance` 仍要保留**。它的作用是在**相关**的候选里排优先级，
  而不是把无关的拉进来 —— 顺序不能反。

## 七、不做什么

写在前面，避免后续讨论反复拉扯：

| 不做 | 理由 |
|---|---|
| 向量检索 / embedding | 需要额外 API 调用或本地模型，与「零原生依赖」冲突。**但要说清代价**：实测证明 2-gram 抓不到跨词语义（「谁养猫」对「养了两只猫」相关度为 0），这个缺口靠结构化 `subject` 只能补一部分。如果以后真的需要语义检索，接入点只有 `queryFacts()` 一个函数，换成向量实现不影响上层 |
| SQLite / 任何数据库 | 见第四节 |
| 知识图谱 | LivingMemory 用四张表做实体关系，是为了「跨会话关系推理」。我们的需求停在「老王和老李是同事」，`subject/predicate` 字符串比较够用 |
| 记忆的可视化界面 | 有锅巴面板。图谱可视化对「说话像人」没有帮助 |
| 跨群记忆合并 | 隐私边界。A 群说的私事不该在 B 群被提起 |
| 记忆的「情感权重」 | 无法客观度量，容易变成给每条记忆打分的伪科学 |
| 人格自动演化（从聊天中学风格） | 效果不可控，容易把口头禅学成复读。想调整就让用户手改 yaml |
| 多机器人共享记忆 | 当前架构是单进程单实例 |

## 八、风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 群级配置写在 `config.yaml` 里，群多了会很长 | 可维护性 | 锅巴面板可编辑；也可以后续挪到独立的 `data/group-presets.json` |
| 冲突消解误判（把不冲突的当冲突） | 丢信息 | 只在 `subject` **和** `predicate` 都相同且 confidence 不降低时才覆盖；被覆盖的保留可查 |
| 模型给不准 `subject/predicate` | 功能退化为现状 | 设计成可选字段，没给就走原路径 |
| 相关性门槛误杀 | 该注入的记忆没注入 | 阈值默认 0（只要有 2-gram 重合就放行），只在完全无关时拦截 |
| 注入内容变多导致 prompt 变长 | 成本 | `profile` 限 100 字；记忆总量受 `injectMaxChars`（1200 字）约束，再受 `context.maxChars` 裁剪 |
| 画像被群友诱导改写 | 人设被污染 | 画像只在明确配置了 `profileEnabled` 时才更新，且不接受「你要记住」类指令（复用现有防注入约束） |

## 九、与两个参考实现的对比

两个项目给了**相反的答案**，我们卡在中间，所以各借一半。

### 9.1 st-memory-enhancement：让模型少犯错

SillyTavern 的表格记忆插件，v2.2.19，1081 行单文件 JS，**无许可证**。
用户定义表格结构（成员表/事件表/物品表），模型在回复末尾输出 `insertRow(...)`，
插件解析后写进表，全量注入不做检索。

**它的核心判断**：不问模型「什么值得记」（开放问题，答案不可控），
而是先定好列，让模型只能往里填（结构约束）。

**我们借的**：

| 机制 | 我们怎么用 | 期 |
|---|---|---|
| schema 约束 | 契约里给「该记哪几类」的锚点，代替抽象的「值得长期记住」 | 一期 |
| 读写开关分离 | `memory.inject` / `memory.write` 拆成两个 | 一期 |
| 操作式协议 | 未来支持 `add/update/delete`，而不是只能追加 | 三期 |
| 幂等保护 | 同一来源消息不重复落库（编辑消息会重新解析） | 二期 |

**我们不借的**：全量注入（记忆量装不下）、记忆存聊天记录（我们要跨重启跨群）、
表格 UI（有锅巴）、用户手工维护（群友不会为了机器人填表）。

详细的机制拆解见 **[st-memory-可借鉴点分析.md](./st-memory-可借鉴点分析.md)**。

> 为什么这个项目对我们更重要：它的痛点是「模型记歪了」，我们的痛点也是。
> 而 LivingMemory 的痛点是「数据太多找不回来」，我们还没到那个量级。

### 9.2 LivingMemory：怎么在大数据量下检索

**它是什么**：[astrbot_plugin_livingmemory](https://github.com/lxfight-s-Astrbot-Plugins/astrbot_plugin_livingmemory)，
AstrBot 的长期记忆插件，v2.8.2，AGPL-3.0。约 2 万行 Python。

**它的体量**：SQLite + FTS5 全文索引 + FAISS 向量 + 四张图谱表；四路检索（文档关键词 / 文档向量 /
图谱关键词 / 图谱向量）融合；五态生命周期（active→dormant→superseded→expired→forgotten）；
影子代际索引重建；2D/3D 图谱可视化。

**它解决的是什么问题**：通用 Agent 助手要跨会话记住用户偏好、项目进展、人物关系，
数据量到万级，需要语义检索和关系推理。这决定了它必须上向量库和图数据库。

**我们解决的是什么问题**：「这个群里谁是谁、最近聊过什么」。数据量几百条，
查询就是「刚才那句话提到了谁」。两个问题的复杂度天花板差了两个数量级。

### 借了哪些机制

| 机制 | 它的做法 | 我们的用法 | 落在哪期 |
|---|---|---|---|
| **类型化 TTL** | 事件 7 天 / 计划 2 天 / 事实 180 天 / 关系 90 天 / 偏好 60 天 | 同参数。**替代原计划的 episodes 分层** | 二期 |
| **访问强化** | 访问降低有效衰减率；每次衰减后访问次数 ×0.5 | 召回时 `accessCount += 1`，打分加 `min(0.3, n*0.02)` | 二期 |
| **字符预算** | 单次 6000 字，单条 800 字，top_k=5 | 单次 1200 字（我们的上下文总量只有 8000） | 一期 |
| **查询意图调权** | 关系词 → 图谱 +0.2；时间词 → 图谱 +0.1 | 查询含时间词时提高 freshness 权重 | 二期 |
| **MMR 多样性** | `mmr_lambda=0.7` | ~~简化版：注入时相似度 >0.7 只留一条~~ **实测后放弃**：2-gram 分不开「换个说法」（0.08~0.40）和「同主体不同方面」（0.07~0.43），区间完全重叠。见第六节的修正说明 | ~~二期~~ |
| **访问统计合并落盘** | 3 秒窗口合并成一次更新 | 沿用现有 `deferred` + `flushMemory()` | 一期 |

### 没借的，和为什么

| 它的技术 | 不用的理由 |
|---|---|
| FAISS + Embedding Provider | 需要额外配置一个嵌入模型。它自己的 README 都在警告「Embedding 留空会回退到第一个可用 Provider，容易选错或导致索引初始化失败」—— 装个陪聊插件要先配嵌入服务，这个门槛我们不想加 |
| SQLite + FTS5 + 触发器 | 原生依赖，编译失败会让插件起不来。这是本项目从第一天就划的红线 |
| 四张图谱表 | 我们对「关系」的需求还停在「老王和老李是同事」，用 `subject/predicate` 字符串比较就够 |
| 2D/3D 可视化 | 有锅巴面板。图谱可视化对「让机器人说话像人」没有帮助 |
| 影子代际重建 / 迁移框架 / 7 天备份 | 我们的数据几百 KB，出问题删了重建就行 |
| 读者-写者锁 / WAL / busy_timeout | 单进程单事件循环，没有并发写 |
| 五态状态机 | 两态够用：有效 / 已被取代。再加 dormant 和 forgotten 是给万级数据管理用的 |

### 一个反面参考

它的架构文档里有一条「已知限制」值得记下来：

> 异步落盘是防抖的，**进程强杀可能丢失最后一次刷盘**

我们在 v1.0.1 修过一模一样的问题（`clearMemory` 是 fire-and-forget，删完立即重启记忆会复活）。
引进任何「异步写入 + 缓冲」的设计时，都要回答「进程被 kill 时丢什么」。

另一个：它的记忆条目有 `memory_sources` 表存原文，理由是「保证有记忆必有可追溯原文」。
我们没做这个 —— 但我们也没有「模型总结出一段话」的环节，每条记忆就是一行原文，
本身就可追溯。将来如果做「摘要合并」，这一条就必须补上。
