# 模拟测试报告：TRSS-Yunzai + LLBot + 伪人插件

> 被测对象：`chatgpt-bym`（伪人模式独立插件，剥离自 `chatgpt-plugin`）
> 目标环境：TRSS-Yunzai v3.1.3 + LuckyLilliaBot 8.3.2（LLBot 侧视为已正常运行）
> 测试日期：2026-10-25
> 结论摘要：**33 个用例，修复后全部通过；过程中发现 2 个真实缺陷（均已修复）、1 个会直接让插件失效的使用约束**

## 一、测试目标与范围

### 1.1 要回答的三个问题

| # | 问题 | 为什么重要 |
|---|---|---|
| Q1 | 按云崽 Miao 分支写的插件，放到 **TRSS** 上能不能被正确加载？ | TRSS 与 Miao 的插件生命周期、事件字段并不完全相同，路径/字段对不上会「加载成功但永不响应」 |

## 二、测试环境与仿真方法

### 2.1 为什么不直接起一个真 TRSS

真 TRSS 启动的硬依赖：Redis（启动第一个动作就连接）、`pnpm i` 全量依赖（含 puppeteer/Chromium，数百 MB）、一个真实 OneBot 连接。这些与「验证插件逻辑」无关，却会引入大量环境噪声。

因此采用**分层仿真**，只在必要处使用真代码：

| 层次 | 被测者 | 实现方式 | 保真度 |
|---|---|---|---|
| 协议层 | LLBot 反连参数 | 用 `ws` 起服务端，**复刻 `lib/bot.js` 的 `wsConnect` 判定**（404 / 401 / upgrade） | 判定分支 1:1，不含 OneBot 协议体 |
| 加载层 | 插件注册 | **复刻 `lib/plugins/loader.js` 的 `loadPlugin`**：两次 `new`、`rule.reg` 编译、priority 升序 | 高 |
| 分发层 | 触发与发送 | **复刻 `deal()` 主流程**：黑白名单 → dealEvent → `only_reply_at` 短路 → rule 依次匹配 → 返回值语义 | 高 |
| 发送层 | `e.reply` | **复刻 `loader.reply` 的包装**：`quote`、`{recallMsg}`、以及「连用户原消息一起撤」 | 高（这处细节正是本次要验的） |
| 业务层 | 插件本体 | **原始源码，未做任何改动**（同步复制进仿真目录） | 100% |
| 模型侧 | 上游 API | 本地 HTTP 假服务，可切换 200 / 401 / 500 / 空响应，记录完整请求体 | 覆盖 OpenAI 兼容协议的必要子集 |

### 2.2 仿真目录布局

```
sim-lab/
├── lib/plugins/plugin.js        # TRSS 插件基类桩（保留构造函数语义）
├── plugins/chatgpt-bym/         # 插件源码副本（sync.mjs 同步）
├── sim/
│   ├── host.js                  # 宿主：loader + deal + reply 包装
│   ├── llmMock.js               # 假 OpenAI 服务
│   ├── run.js                   # 业务层 26 个用例
│   ├── ws.js                    # 协议层 7 个用例
│   └── debug-recall.js          # 撤回行为的隔离验证
└── sync.mjs                     # 从 ../../chatgpt-bym 同步源码
```

> 插件里 `import plugin from '../../../lib/plugins/plugin.js'` 是相对路径，所以仿真必须还原「`plugins/<插件>/apps/*.js`」这个物理布局，桩文件才能被解析到。这也是为什么不能直接把插件目录软链到别处。

### 2.3 关键输入条件（全局）

| 条件 | 值 | 说明 |
|---|---|---|
| 触发方式 | `hitKeywords: ['bym']`，`probability: 0` | 概率置 0，确保只有关键词能触发，便于区分用例 |
| 冷却 | `cooldownSeconds: 0`，`maxPerHour: 0` | 默认全关，只在 G2.7 / G2.8 单独打开 |
| 拟人化延迟 | `typingDelay: {minMs:1, perCharMs:0, maxMs:2}` | 压到毫秒级，否则每个用例要等 6 秒 |
| 群上下文 | `context.enable: false` | 默认关，G3.5 / G3.6 单独打开 |
| 模型返回 | 固定文本（10 字） | G3.4 单独换成 50 字长文本 |

## 三、场景设计与执行结果

### 3.1 协议层（P1–P7）

| 编号 | 输入条件 | 预期 | 实际 | 结果 |
|---|---|---|---|---|
| P1 | `ws://127.0.0.1:2536/OneBotv11` | 101 升级 | 101 | 通过 |
| P2 | `/onebotv11`（小写） | 404 | 404 | 通过 |
| P3 | `/OneBot11`（少 v） | 404 | 404 | 通过 |
| P4 | `/OneBotv11/extra`（多一段） | 101（TRSS 只取 pathname 第一段） | 101 | 通过 |
| P5 | `server.yaml` 配了 `auth`，客户端不带 Header | 401 | 401 | 通过 |
| P6 | 同上，但带上正确 `Authorization` | 101 | 101 | 通过 |
| P7 | 连一个没有服务的端口 | ECONNREFUSED | ECONNREFUSED | 通过 |

**观察**：

- 路径**大小写敏感**且**必须拼写完整**，这是最容易写错的一处；但**多一段路径不会失败**（TRSS 用 `url.pathname.split("/")[1]` 只取第一段），所以 `/OneBotv11/` 尾斜杠是安全的。
- P5/P6 证实了部署指南里的结论：**LLBot 的 `ws-reverse` 只能设 token、不能加自定义 Header**，所以 TRSS 的 `server.auth` 必须留空，否则必然 401。

### 3.2 加载层（G1.1–G1.4）

| 编号 | 预期 | 实际 | 结果 |
|---|---|---|---|
| G1.1 | 注册 2 个类：伪人模式(6000)、伪人模式管理(10) | 伪人模式(6000) + 伪人模式管理(10) | 通过 |
| G1.2 | 全部 `rule.reg` 为 RegExp | 全部编译成功 | 通过 |
| G1.3 | 每类被 `new` 两次，且两实例不同 | 每类 init ≠ rule | 通过 |
| G1.4 | 配置生成到指定目录 | `config.yaml` 存在 | 通过 |

**观察**：`index.js` 导出 `{ apps }`，TRSS 的 `module.apps ? {...module.apps} : module` 正好命中，多导出的 `pluginRoot` 被自动忽略——这个约定必须保持，否则会把非类导出当插件处理（已被 `if (!p?.prototype) continue` 兜住）。

**G1.3 是一个容易忽视的约束**：TRSS 会 new 两次，`deal()` 里**每条消息还会再 new 一次并传入 `e`**。所以插件的构造函数里**不能有任何只该执行一次的副作用**（起定时器、写文件、建连接）。本插件的构造函数只做 `super({...})` 和读配置，符合要求；冷却状态放在模块级 `Map` 里，也确实不依赖实例。

### 3.3 触发闸门（G2.1–G2.10）

| 编号 | 输入条件 | 预期 | 实际 | 结果 |
|---|---|---|---|---|
| G2.1 | `enable: false` | 0 条 | 0 条 | 通过 |

| G2.4 | 消息 @ 了别人 | 不插话 | 0 条 | 通过 |
| G2.5 | 含关键词 `bym`，概率 0 | 触发 | 1 条 | 通过 |
| G2.6 | 无关键词，概率 0 | 不触发 | 0 条 | 通过 |

- **G2.9**：TRSS 在 `deal()` 里有一行 `if (!e.only_reply_at) return`，位置在 rule 匹配**之前**。也就是说只要 `group.yaml` 的 `onlyReplyAt` 不是 0、且消息没 @bot，**伪人插件连被调用的机会都没有**。排查「插件装了但不说话」时，这是第一顺位。
- **G2.10**：`other.yaml` 出厂自带 `blackGroup: [213938015]`，命中同样在插件之前被拦掉。

|---|---|---|---|

## 四、发现的差异与问题

### 问题 1（致命，已修复）：js-yaml 5.x 没有 default 导出，插件启动即崩

| 项 | 内容 |
|---|---|
| 发现方式 | 仿真环境用 `npm i js-yaml` 装了 **5.5.0**，首次运行直接抛错 |
| 现象 | `SyntaxError: The requested module 'js-yaml' does not provide an export named 'default'` |
| 根因 | js-yaml 4.x 是 CJS（有 default）；5.x 改为纯 ESM，只提供命名导出。原代码 `import yaml from 'js-yaml'` 依赖 default |
| 影响面 | **100% 启动失败**。不是「某个功能不好用」，是插件整个加载不起来 |
| 触发条件 | 全新安装时未锁版本、或用户手动 `pnpm add js-yaml` 升到 5.x |
| 修复 | `config/config.js`、`models/preset.js` 改为 `import * as YAML from 'js-yaml'` + `const yaml = YAML.default ?? YAML`，两代版本通吃 |
| 回归 | 在 4.3.2 与 5.5.0 下均验证通过（仿真用 5.5.0，插件目录用 4.3.2） |

> 这是本次测试最有价值的产出：单元测试用的是插件自带 `node_modules`（4.x），永远走不到这条路径；只有在一个「干净安装」的环境里才会暴露。

### 问题 2（行为缺陷，已修复）：TRSS 下 `recallSeconds` 会双重撤回并误撤用户消息

| 项 | 内容 |
|---|---|
| 发现方式 | G5.1，观察 `e.reply` 的实际撤回调用 |
| 现象 | 开启 `speaking.recallSeconds` 后：① 同一条回复被撤两次；② **触发它的用户消息也被撤回** |
| 根因 | 两处叠加：<br>① 插件传了 `e.reply(seg, false, {recallMsg: N})`；<br>② 插件又用返回的 `message_id` 自己 `group.recallMsg()` 撤一次。<br>而 TRSS 的 `loader.reply` 对 `recallMsg` 的实现是：撤回复 **+ 撤用户原消息**（`lib/plugins/loader.js`） |
| 影响面 | 功能可用但观感差：群友发言被无故撤回（在「伪人陪聊」场景下非常突兀），且第二次撤回必然失败（只留下日志噪音） |
| 修复 | 不再传 `{recallMsg}`，统一由插件自己的 `scheduleRecall` 只撤自己这一条。跨分支（Miao / TRSS）行为一致 |
| 回归 | G5.1 通过；隔离验证只有 1 次撤回，目标就是自己发出的 `r1` |

### 问题 3（使用约束，非代码缺陷）：`onlyReplyAt` 非 0 时伪人完全收不到消息

G2.9 证实了这条链路：`group.yaml` 的 `onlyReplyAt` 只要不是 0，TRSS 在进入插件匹配前就 `return` 了。**装伪人类插件的群必须 `onlyReplyAt: 0`**，否则表现为「机器人其他功能正常，就是不会主动说话」。

同样，`other.yaml` 出厂自带的 `blackGroup: [213938015]` / `blackUser: [528952540]` 也会在插件之前拦掉（G2.10）。

### 问题 4（测试工具缺陷，非产品问题 ×3）

如实记录，避免把「测试写错了」当成「代码有 bug」：

| 编号 | 误判 | 真实原因 |
|---|---|---|
| G3.4 | 以为「分段丢内容」（只发出 30 字） | 等待逻辑写成「收到第一条就返回」，第二条还在拟人化延迟里没发出去。改为「有发送且连续 250ms 无新增」 |
| G3.7 | 以为「回退模式没生效」 | 断言拿「普通群友」当特征词，而预设文件 `bym_default.yaml` 里本来就有这四个字。改用 contextualPrompt 独有的「自然的切入点」 |
| G5.1 | 全套里看到撤回 2 次 | 上一条用例的定时器残留污染了共享的 `recalls` 数组。写 `debug-recall.js` 隔离验证后确认只有 1 次 |

> 这三处恰好说明一件事：**测试断言必须用「只可能出现在该分支」的特征**，否则通过与否都没有意义。

## 五、结论

1. **插件在 TRSS 的加载与分发语义下可以正常工作**：`apps` 导出约定、`rule.reg` 字符串、`priority` 升序、返回 `false` 继续传递，全部符合预期。
2. **协议层的参数是最容易出错、也最容易验证的一环**：路径 `/OneBotv11` 大小写敏感、`server.auth` 必须留空、端口 2536 三处对齐，7 个用例覆盖了全部失败分支。
3. **两个真实缺陷都出在「跨分支差异」上**：`js-yaml` 的模块格式、`e.reply` 的 `recallMsg` 语义——单测在 Miao 语境下永远发现不了。这类问题只能靠「在目标分支的语义下跑一遍」暴露。
4. **修复后 33 个用例全部通过**，且修复没有引入回归（插件的 38 项单测 + 仿真 33 项同时绿）。

## 六、未覆盖范围与遗留风险

| 未覆盖项 | 风险 | 建议验证方式 |
|---|---|---|
| 真实 QQ 消息收发 | 图片、@、回复引用在真实 OneBot 报文下可能与 mock 不同 | 在测试群各发一条纯文本/图片/引用，看日志里的 `payload.messages` |
| OneBot 生命周期与心跳 | `meta_event` 处理异常时插件无感，但连接可能反复重建 | 观察 TRSS 日志的 `建立连接` / `断开连接` 频率 |
| TRSS 的 `msgThrottle` | 同一用户 1 秒内发相同内容会被 TRSS 丢弃（在插件之前） | 连发两条相同消息，确认第二条本就不该有响应 |
| Milky / Satori 协议 | 端口与路径不同（Milky 3010、Satori 5600/`/v1`），本次未验证 | 改用主动连接方案时重新跑一遍 G2/G3 |
| Chromium 渲染 | 伪人本身不发图卡，但同群其他插件可能需要 | 与本插件无关 |
| 长时间运行 | 冷却 `Map` 与 LLBot 配置热重载的交互未测 | 挂机数小时看内存与冷却是否漂移 |

## 七、复现方式

```bash
cd sim-lab
node sync.mjs          # 把 ../../chatgpt-bym 的最新源码同步进来
node sim/ws.js         # 协议层 7 项
node sim/run.js        # 业务层 26 项（退出码非 0 表示有差异）
node sim/debug-recall.js   # 撤回行为隔离验证
```

依赖：`sim-lab` 目录内已装 `js-yaml` + `ws`，无需再次安装。
`run.js` 会把配置与数据写到系统临时目录，运行结束自动删除，不碰插件里的真实配置。
