# 记忆方案 · Yunzai 适配版

> 前面两份文档解决「记忆应该怎么设计」（`人格与长期记忆方案.md`）和「别人怎么做的」
> （`st-memory-可借鉴点分析.md`、方案文档第九节）。
>
> 这一份解决另一个问题：**这些设计放到 TRSS-Yunzai 上跑，哪些能照做、哪些必须改。**
>
> 结论先说：机制基本都能落地，但**有三处必须先修**才能谈记忆 ——
> 宿主给的 10 秒优雅退出窗口我们没用、热更新会漏掉文件监听、首次读盘会阻塞消息处理。
> 这三个问题在写这份文档时就已存在，**A 期已完成（v1.3.2）**，见 5.3 节的验收结果。

## 一、我们的运行环境（实测事实）

| 项 | 事实 | 来源 |
|---|---|---|
| 宿主 | TRSS-Yunzai **3.1.3**，ESM（`"type": "module"`） | `package.json` |
| 进程管理 | **pm2 单实例**，`max_memory_restart: 512M`，`kill_timeout: 10000` | `config/pm2.yaml` |
| 崩溃处理 | `exp_backoff_restart_delay: 1000`，崩溃后指数退避重启 | 同上 |
| 运行模型 | 单进程单线程，所有插件共用一个事件循环 | Node 运行时 |
| 宿主自带的库 | `node-schedule`（定时任务）、`chokidar`（文件监听）、`level`、`sequelize`、`redis`、`express` | `package.json` |
| 我们的依赖 | 只有 `js-yaml` | `package.json` |
| 我们的代码量 | 3900 行 JS，9 个模块 | — |

`kill_timeout: 10000` 那行在 pm2 配置里有明确注释：

> pm2 停止/重启进程的等待时间，需大于插件退出清理的耗时，
> 否则进程会被 SIGKILL 强杀，插件持有的子进程将成为孤儿

**翻译成我们的问题**：pm2 会给进程 10 秒做收尾，超过就 `SIGKILL`。
这 10 秒是给我们落盘记忆用的 —— 但我们现在**没有注册任何退出钩子**，等于白白浪费。

## 二、插件机制里与记忆直接冲突的五件事

### 2.1 每条消息都会 `new` 一次插件实例

```js
// lib/plugins/loader.js（TRSS 3.1.3）
const init = new p()        // 第一个实例：跑 init()、收集 task、登记 cleanup
...
const plugin = new p()      // 第二个实例：注册进 priority，处理消息
```

而且 `deal()` 里每条消息还会再 `new` 一次并把 `e` 传进去。

**影响**：任何记忆状态都不能挂实例字段。`self.memoryCache = {}` 在第二条消息就没了。

**我们现状**：✅ 已经是模块级（`models/memory.js` 的 `store` 变量），构造器是空的。

### 2.2 热更新会重新 import 整个模块

加载器用 chokidar 监听插件目录（`this.watch(val.name, app.name)`），
文件一变就 `unloadPlugin` + 重新加载。重载时模块重新求值，**所有模块级状态清空**：

| 状态 | 重载后 | 要紧吗 |
|---|---|---|
| `memory.js` 的 `store`（内存副本） | 丢失，下次从 `memory.json` 重读 | ⚠ 依赖磁盘 |
| `dedup.js` 的三张表 | 清空 | 不要紧（几秒窗口） |
| `rateLimit.js` 的冷却记录 | 清空 | 不要紧（最多多发一条） |
| `preset.js` 的缓存 | 清空 | 不要紧（5 秒 TTL） |

**结论**：记忆**必须**以磁盘为准，内存只是缓存。当前设计符合这一点，但要确保每次写入都尽快落盘。

### 2.3 卸载时只清理由 `init()` 登记的资源

```js
// plugin.js
addCleanup(dispose, restore)  // 只能在 init() 里调才会被登记
```

```js
// loader.js 的 loadPlugin
if (init.init && (await init.init()) === "return") { ... }
...
if (init[PluginCleanup]?.length) { this.initializerMap.get(file.name).add(init) }
```

我们的插件**没有 `init()` 方法**，所以 `initializerMap` 里没有我们。
后果：`unloadPlugin` 时不会调我们的 dispose，而 `index.js` 里这句

```js
config.load().watch()   // 注册了 fs.watchFile
```

**永远不会被 `unwatch`**（`config.js:324` 的 `unwatch()` 方法从头到尾没人调用）。

热更新一次 → 多一个 watchFile 回调 → 改配置时可能触发多次 `load()`。
改十次插件文件，就挂十个。

**这是现存缺陷，不是记忆功能带来的。** 修复只要给插件加一个 `init()`：

```js
init () {
  this.addCleanup(() => {
    config.unwatch()
    flushMemory()          // 顺便把记忆刷盘
  })
}
```

### 2.4 定时任务用 `task` 字段，宿主统一调度

```js
// plugin.js
task = { name: "", fnc: "", cron: "" }     // cron 是 6 段（秒 分 时 日 月 周）
```

加载器用 `node-schedule` 注册，卸载时 `i.job?.cancel?.()` 自动取消。

**但**：cron 任务是进程内的，**重启后不补跑**。20:00 的任务，进程 19:59 重启，这一天就跳过了。

**对我们方案的直接影响**：之前决定「不做每日衰减，改用访问强化」，理由是「少一个后台任务」。
现在看这个决定依然成立，而且理由更强 —— 定时任务在 Yunzai 上不是不可用，而是
**不可靠地可用**（热更新会重排、重启会跳过）。用它做衰减，衰减就变得不规律。

TTL 过期是**读时计算**（`expiresAt < now` 就跳过），不依赖定时任务 ✅

### 2.5 512M 内存上限，超了 pm2 直接重启

`max_memory_restart: 512M` 是进程级上限，云崽本体（含 puppeteer、express、数据库连接）
通常占 200-400M。留给插件的余量不大。

**记忆的内存占用估算**：

```
200 条/群 × 50 群 × 平均 60 字 ≈ 600KB 文本
加上对象开销（每条约 300 字节）≈ 3MB
```

3MB 完全没问题。**但如果哪天想把 `memory.json` 换成"全量缓存 + 索引"，就要盯着这条线。**
这也是不引入向量库的一个附带理由 —— FAISS 索引本身就要几十 MB。

## 三、方案整体思路（适配后）

### 3.1 一张图

```
                    ┌─────────────────────────────────────┐
   群消息 ──────────►│ ① 去重与回声（内存，可丢）           │
                    └──────────────┬──────────────────────┘
                                   ▼
                    ┌─────────────────────────────────────┐
                    │ ② 触发闸门（含 @必回）               │
                    └──────────────┬──────────────────────┘
                                   ▼
                    ┌─────────────────────────────────────┐
                    │ ③ 记忆召回                           │
                    │   · 内存缓存（首次同步读盘，之后只读内存）│
                    │   · TTL 过滤（读时算，无定时任务）      │
                    │   · 相关性门槛 → 访问强化 → 分节注入    │
                    └──────────────┬──────────────────────┘
                                   ▼
                    ┌─────────────────────────────────────┐
                    │ ④ 生成 + 契约解析（记忆副产品）        │
                    └──────────────┬──────────────────────┘
                                   ▼
                    ┌─────────────────────────────────────┐
                    │ ⑤ 落盘：deferred 合并 → 异步写队列      │
                    │   + SIGTERM/SIGINT 兜底 flush         │
                    └─────────────────────────────────────┘
```

### 3.2 三条设计原则（都是被 Yunzai 逼出来的）

**原则一：磁盘是唯一真相，内存只是缓存。**

因为热更新随时会清空模块状态。所以：
- 任何"很重要不能丢"的状态必须落盘
- 落盘要快（异步队列 + 合并写），因为不知道什么时候会被重载
- 内存缓存只是为了避免每轮都读盘

**原则二：不用定时任务维护记忆。**

因为 cron 任务在热更新和重启时都不保证执行。所以：
- TTL 过期 → 读时计算
- 访问强化 → 召回时就地累加
- 满额淘汰 → 写入时触发

**全部是「用到才做」，没有「定期做」。** 这样无论进程怎么重启，行为都一致。

**原则三：所有 IO 都要能被中断，且失败不阻塞消息。**

因为 512M 上限和 10 秒 kill 窗口都意味着进程可能随时死。所以：
- 写盘失败只记日志（已有）
- 首次读盘失败 → 用空记忆继续（已有）
- 退出时尽力 flush，但不 `process.exit()`（会打断其他插件）

### 3.3 记忆的数据形态（最终版）

沿用方案文档的分层，但按 Yunzai 的约束收敛：

```json
{
  "version": 2,
  "groups": {
    "123456": {
      "profile": { "about": "", "updatedAt": 0 },
      "facts": [
        {
          "id": "m3k2j1",
          "fact": "张三在字节做后端",
          "type": "fact",
          "expiresAt": 1745500000,
          "accessCount": 3,
          "lastAccessAt": 1735000000,
          "importance": 0.8,
          "subject": "张三",
          "predicate": "职业",
          "supersededBy": null,
          "at": 1730000000
        }
      ]
    }
  }
}
```

**没有 `episodes` 数组**（被 `type` + `expiresAt` 取代），
**没有向量字段**，**没有独立索引文件**。一个 `memory.json` 装完。

## 四、与两份参考方案的差异

### 4.1 对照表

| 维度 | LivingMemory（AstrBot） | st-memory（ST 表格） | 我们（Yunzai） |
|---|---|---|---|
| 存储 | SQLite + FTS5 + FAISS | 聊天记录内嵌 | 单 JSON 文件 |
| 检索 | 四路融合 | 无（全量注入） | 2-gram 单路 + 门槛 |
| 生命周期 | 五态 + 每日衰减 + TTL | 无（人工删行） | **两态 + TTL（读时算）** |
| 记忆来源 | 自动总结 | 用户定义 schema | 回复副产品（+ 契约锚点） |
| 定时任务 | 有（每日衰减、每周整合） | 无 | **无**（刻意） |
| 并发控制 | WAL + 读写锁 | 无（单用户） | 无（单进程单线程） |
| 退出保证 | 有 flush 钩子（但有已知丢数据风险） | 无（前端，浏览器关就没了） | **要有（当前缺失）** |
| 内存占用 | 几十 MB（FAISS 索引） | 几百 KB | **约 3MB** |

### 4.2 为什么砍掉「每日衰减」和「定时整合」

这是和 LivingMemory 最大的分歧。

| 它的做法 | 我们的取舍 |
|---|---|
| 每日定时衰减 importance | **不做**。用访问强化代替 —— 被召回的加分、没被召回的天然沉底，排序效果等价，且不需要调度 |
| 每周整合（10 条压 1 条） | **暂不做**。200 条上限在每天 10 条的群要 20 天才满；真满了优先解决「淘汰得不合理」，而不是压缩 |
| 五态状态机 | **两态**：有效 / 已被取代。dormant 和 forgotten 是给万级数据管理用的 |
| FTS5 全文索引 | **不做**。200 条线性扫一遍是微秒级，建索引纯属浪费 |

**共同原因**：定时任务在 Yunzai 上不可靠（2.4 节）。凡是"定期做"的事，
要么改成"用到才做"，要么就不做。

### 4.3 从 ST 表格借的，怎么落地

| 它的机制 | 我们的落地 | 差异 |
|---|---|---|
| 表格 schema | 契约里给「记哪四类」的锚点 | 不建真表，只给 prompt 锚点 |
| `insertRow/updateRow/deleteRow` | 未来支持 `memoryOps` | 保留纯文本 `memory:[...]` 兼容 |
| 幂等（记住上次解析原文） | 落库时带来源消息 id + 内容哈希 | 内存里只留最近 20 条哈希 |
| 读写开关分离 | `memory.inject` / `memory.write` | 同 |
| `deep` 注入深度 | 记忆单独成一条消息，不掺进当前消息 | 我们的预算逻辑要跟着改 |
| `{{GET::表:格}}` 宏 | 暂不做（依赖稳定的 subject） | — |

## 五、适配考量：运行环境 / 资源 / 插件机制

### 5.1 运行环境

**ESM 与依赖**：云崽是 `"type": "module"`，我们的插件也是。`js-yaml` 的版本兼容问题
已经在 1.0.1 修过（4.x CJS / 5.x 纯 ESM 都兼容）。

**Node 版本**：我们用了 `structuredClone`（Node 17+）、`fs.promises`、`AbortController`。
TRSS 3.1.3 要求 Node 18+，满足。

**❌ 不能用宿主的依赖**：虽然 `node_modules` 提升让我们能 `import 'level'`，
但那是宿主装的。宿主升级删掉它，我们的插件就崩了。
**只依赖自己 `package.json` 里声明的东西** —— 目前是 `js-yaml` 一个。

**多账号**：`Bot.bots` 支持多账号。同一台机器上的两个机器人号如果在同一个群，
它们共享同一份群记忆（因为按 `group_id` 存）。这通常是想要的（同一个"人设"在两个号上），
但如果是两个不同的角色，就会串味。**当前不做区分，文档里写清楚。**

### 5.2 资源限制

| 限制 | 影响 | 应对 |
|---|---|---|
| 512M 内存上限 | 超了 pm2 重启 | 记忆控制 3MB 内；不做全量索引/向量 |
| 10 秒 kill_timeout | 退出时要落盘 | ✅ 已注册 SIGTERM/SIGINT flush（1.3.2），单项任务超时 5 秒 |
| 单线程事件循环 | 同步 IO 会卡住所有消息 | 首次读盘一次（可接受）；写盘走异步队列 |
| 磁盘 | Docker 可能没挂 data/ | 文档要求挂载；启动时检测并 warn |

**首次读盘的耗时估算**：`memory.json` 几百 KB，`readFileSync` + `JSON.parse` 约 5-15ms。
只在进程启动后第一次访问记忆时发生（`ensureLoaded()` 懒加载）。
这 15ms 期间所有消息处理停摆。**可接受，但要知道它存在。**

如果将来记忆涨到几 MB，这 15ms 会变成 100ms+，那时候要做**分群懒加载**
（只读当前群那份）。不过那就得把单个 `memory.json` 拆成 `memory/<群号>.json` 了。

### 5.3 插件机制（三个必须修的现存问题）

| # | 问题 | 现在的影响 | 状态 |
|---|---|---|---|
| **A** | 没有退出钩子 | pm2 给 10 秒收尾，我们不用；未落盘的记忆丢失 | ✅ 已修（1.3.2） |
| **B** | `config.watch()` 未登记 cleanup | 热更新一次多一个 watchFile；改配置触发多次 load | ✅ 已修（1.3.2） |
| **C** | `unwatch()` 从未被调用（死代码） | 同 B | ✅ 已修（1.3.2） |

**A 的实际实现**（`utils/lifecycle.js`，要注意不能 `process.exit()`，
否则打断其他插件的收尾）：

```js
const shutdown = createShutdown({
  tasks: [
    // 1.4.0 起用 disposeMemory() 而不是 flushMemory()：它多两件事 ——
    // 把攒批的访问计数刷出去，并停掉那个 3 秒定时器
    { name: 'memory', run: () => disposeMemory() },
    { name: 'config-watcher', run: () => config.unwatch() },
  ],
})
installShutdownHooks(shutdown)
```

三层保护：

1. **幂等** —— 已跑完返回同一份结果；正在跑返回 `{ran:false}`，不重复落盘。
2. **失败隔离** —— 一项抛错不影响另一项，失败打 warn。
3. **独立超时**（默认 5 秒）—— 卡住的一项（磁盘满、网络盘挂起）不会拖死另一项，
   也不会耗尽 pm2 的 10 秒窗口被判 SIGKILL。

**B 的实际实现**（`apps/bym.js` 的插件类）：

```js
init () {
  this.addCleanup?.(
    async () => { config.unwatch(); await flushMemory() },   // dispose
    () => config.watch(),                                    // restore：热更新失败时挂回去
  )
}
```

`addCleanup` 是 TRSS 3.x 的接口，Miao 分支没有，所以判空。
`dispose` 返回的 Promise 会被 loader 的 `Promise.allSettled` 等待，卸载期间的写盘能完成。

**C 的附带修复**：`unwatch()` 现在会 `clearTimeout(this._timer)` ——
防抖定时器已经排上的话，光解绑 watchFile 是不够的，它仍会触发一次 `load()`。

#### 验收结果（`sim-lab/sim/verify-a-phase.js`，8 项全过）

| 检查 | 方法 | 结果 |
|---|---|---|
| 钩子挂上了 | `process.listenerCount('SIGTERM')` 增加 | ✅ |
| 信号能落盘 | 只进内存的 `deferred` 写入 → `process.emit('SIGTERM')` → 磁盘上出现 | ✅ |
| 加载时监听 | `config._watcher` 非空 | ✅ |
| cleanup 登记了 | 从 `host.instances` 里找到带 `[PluginCleanup]` 的实例 | ✅ |
| 卸载时解绑 | `host.unload()` 后 `config._watcher` 为 null，`disposed > 0` | ✅ |
| 重复卸载安全 | 第二次 `disposed === 0` | ✅ |
| timer 被清 | `unwatch()` 后 `_timer === null` | ✅ |

**注意**：这些是仿真验证（`sim-lab` 自建的 TRSS 桩件）。`SIGTERM` 那条在真机上还要再走一遍 ——
仿真只能证明我们的处理器会响应 `process.emit`，证明不了 pm2 真的会在 SIGKILL 前发信号。

### 5.4 与 chatgpt-plugin 共存

两个插件都监听群消息。记忆按 `group_id` 存，各存各的，不冲突。
但两个都开伪人模式会抢话 —— 这是已知问题（部署文档 5.14），与记忆无关。

## 六、实施分期（按 Yunzai 的可行性调整）

| 期 | 内容 | 为什么这个顺序 | 状态 |
|---|---|---|---|
| **A（先修地基）** | 退出钩子 + cleanup 登记 + `unwatch` 接上 | 这三件事与记忆无关但**记忆依赖它们**：没有退出钩子，任何落盘设计都不可靠 | ✅ 1.3.2 |
| **B（记忆可用性）** | 相关性门槛 + 字符预算 + 契约锚点 + 读写开关 | 改动小、纯 logic、不碰存储格式。直接消掉「拿无关记忆瞎发挥」 | ✅ 1.3.3 |
| **C（人设）** | 群级人设绑定 + 切换指令 + prompt 加群名 | 独立于记忆，可以先做也可以后做 | ✅ 1.4.0 |
| **D（记忆结构）** | `type` + `expiresAt` + `accessCount` + `profile` + 冲突消解 | 第一次改 `memory.json` 结构，要观察 B 期跑一段 | ✅ 1.4.0 |
| **E（记忆质量）** | 幂等 + 摘要合并 + 画像自动维护 | 依赖模型输出质量，需要真实数据 | 未做 |

C 和 D 合并成一批做的，因为两者都改 `chatService` 里同一段 prompt 拼装（人设在前、记忆在后），
分开做要改两遍。

**C 期的端到端验证**（`sim-lab/sim/run.js` 的 G11.1–G11.3）：

| 用例 | 验证什么 | 结果 |
|---|---|---|

## 七、落地风险点

按「会不会出事」排序。

### 🔴 高风险：热更新期间的记忆写入丢失

**场景**：用户改了一个插件文件 → chokidar 触发 → 卸载旧模块 → 重新加载。
如果此时正好有一条消息在处理中，`store` 内存里有新写入但还没 flush，重载后这个写入就没了。

**概率**：低（要求恰好撞上），但热更新很频繁（改配置、装插件都可能触发）。
**后果**：丢一条记忆，不明显。
**缓解**：把 flush 的触发点提前到"每次 `addFact` 之后尽快"（现在是 deferred + 手动 flush，
中间有窗口）。或者接受这个损失（一条记忆而已）。

### 🔴 高风险：Docker 部署没挂 data 卷

**场景**：用户 `docker run` 没挂 `/app/plugins/chatgpt-bym/data`，容器重启后记忆全丢。
**后果**：用户以为是插件坏了。
**缓解**：`config.load()` 时检测 `data` 目录是否在容器内且未挂载（`/.dockerenv` 存在 +
目录 mtime 很新 + 文件数为 0），启动时打 warn。这条在部署文档里也要写。

### 🟡 中风险：多实例共享 data 目录

**场景**：用户跑两个云崽（不同 QQ 号、不同端口）但共用一个 `plugins/` 目录。
两个进程各持一份 `store` 内存副本，轮流全量写 `memory.json` → **后写的覆盖先写的**。
**后果**：记忆随机丢失，且极难排查。
**缓解**：①文档强制要求配 `BYM_DATA_DIR`；②启动时往 `memory.json` 同级写一个
`instance.lock`（含 pid），发现是别的 pid 就 warn。

### 🟡 中风险：契约退化导致记忆静默失效

**场景**：小模型不按 `{say, memory}` 格式返回 → `memoryDegraded` → 退回独立抽取 →
但独立抽取要求 ≥6 条语料 → 不够 → 记忆永远是 0 条。
**后果**：用户以为记忆坏了，但日志里只有 debug 级别的一行。
**缓解**：把「连续 N 轮都没成功记录记忆」提升为 warn，并在 `#bym 状态` 里显示"最近一次
记忆写入时间"。**这个指标比"记忆总条数"有用得多。**

### 🟡 中风险：512M 触顶后重启循环

**场景**：记忆 + 群上下文 + 图片缓存叠加，进程涨到 512M → pm2 重启 → 重启后又涨 → 循环。
**概率**：很低（我们的记忆才 3MB，主要占用是 puppeteer）。
**缓解**：不引入向量库/缓存索引；图片缓存已有 60 条上限 + 5 分钟 TTL。

### 🟢 低风险：首次读盘阻塞

**场景**：进程启动后第一条被触发的消息，要等 `ensureLoaded()` 读完盘（5-15ms）。
**后果**：那条消息的回复晚 15ms，无感。
**缓解**：不需要。但如果记忆涨到几 MB，要改成启动时预热或分群懒加载。

### 🟢 低风险：时区与相对时间

**场景**：`[3天前]` 这种相对时间在注入时算错（服务器 UTC，用户 UTC+8）。
**后果**：模型说错时间。
**缓解**：`formatTime` 已经用本地时区；相对时间在同一台机器上算，不会跨时区不一致。

## 八、部署前提清单（给用户的）

装之前确认这四条，否则记忆会丢：

| # | 前提 | 怎么查 |
|---|---|---|
| 1 | `data/` 目录可写且**持久化**（Docker 要挂卷） | 容器内 `touch data/test && rm data/test` |
| 2 | 一个 `plugins/` 目录只给**一个**云崽实例用，否则配 `BYM_DATA_DIR` | `ps aux \| grep node` 看进程数 |
| 3 | pm2 `kill_timeout` 不小于 10 秒（默认就是） | `cat config/pm2.yaml` |
| 4 | 如果开了 `memory.extract`，模型要能稳定输出 JSON | 看日志有没有 `[bym][memory] 从回复中记录 N 条` |

```bash
# 1. 退出钩子是否生效
kill -TERM <pid>
# 期望日志： [bym] 收到 SIGTERM，记忆已落盘
# 然后检查 memory.json 的 mtime 是否刚刚更新
```
