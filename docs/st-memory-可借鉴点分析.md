# st-memory-enhancement 可借鉴点分析

> 对象：[muyoou/st-memory-enhancement](https://github.com/muyoou/st-memory-enhancement) v2.2.19
> （SillyTavern「记忆增强表格」插件，单文件 `index.js` 1081 行）
>
> 结论先说：**它和 AstrBot 的记忆方案是两个极端**。AstrBot 靠自动抽取 + 向量检索 + 只注入 top-5；
> 这个项目靠**人工定义表格结构 + 全量注入 + 模型自己找**。
> 我们卡在中间，所以两边的机制都只能借一半。
> 最值得抄的是它**用 schema 约束模型该记什么**这件事，而不是它的存储或检索。

---

## 一、它是什么

SillyTavern（酒馆）是 AI 角色扮演的前端。这个插件解决的是 RP 玩家的经典痛点：
聊到 300 楼之后，角色忘了「你是谁」「我们上周去了哪」。

它的答案不是"让模型自己总结"，而是：

> **用户先定义几张表（成员表、事件表、物品表），规定每张表有哪些列。
> 聊天时，模型在回复末尾输出 `insertRow(...)` 这样的指令，插件解析后写进表。**

所以它是**半人工**的记忆系统：schema 人定，内容 AI 填，脏了人改。

体量对比：

| | st-memory-enhancement | astrbot_plugin_livingmemory | 我们（chatgpt-bym） |
|---|---|---|---|
| 代码量 | 1081 行 JS（单文件） | ~2 万行 Python | ~3900 行 JS |
| 存储 | 聊天记录内嵌（`hash_sheets`） | SQLite + FTS5 + FAISS | 单个 `memory.json` |
| 检索 | **没有检索**，全量注入 | 四路融合（BM25/向量/图谱×2） | 2-gram 单路 |
| 记忆来源 | 用户定义 schema，AI 填行 | 自动总结对话 | 回复副产品 `{say, memory}` |
| 依赖 | 无（纯前端扩展） | SQLite + FAISS + Embedding Provider | 无（只有 js-yaml） |

## 二、核心设计思路

### 2.1 schema 先行：先定"记什么"，再让 AI 填

这是整个项目最根本的决定。它不指望模型自己判断「什么值得记」，而是：

1. 用户建表：`成员表`，列 = 姓名 / 身份 / 关系 / 备注
2. 每条消息注入这张表的**当前内容 + 列定义 + 编辑规则**
3. 模型看到「成员表已有 3 行，列是这些」，就知道该往哪填、填什么格式

对比我们现在的做法：

```
模型自由发挥 → 返回 ["张三在字节做后端", "今天好热", "李四养猫"]
                ↑ 质量参差，靠 prompt 约束，靠 importance 打分补救
```

它的做法：

```
模型看到列定义 → 只能往「姓名/身份/关系」里填 → 填歪了下一轮会被自己 updateRow 修正
```

**这是"约束输入"而不是"过滤输出"**。我们一直在做后者（相关性门槛、importance、冲突消解），
它直接让模型没有跑偏的空间。

### 2.2 操作式协议，不是状态快照

模型不改写整张表，只输出**增量操作**：

```
<tableEdit>
insertRow(0, {"姓名": "张三", "身份": "后端开发"})
updateRow(0, 2, {"关系": "同事"})
deleteRow(0, 3)
</tableEdit>
```

好处是**可逐条校验、可排序、可幂等**，这三点 JSON 快照都做不到（详见第四节）。

### 2.3 记忆随对话走，不建独立库

表格数据以 `hash_sheets` 的形式**存在聊天记录里**，跟着消息一起保存。
删聊天 = 删记忆，导出聊天 = 导出记忆，回滚 = 记忆自动回滚。

这个设计对 RP 场景是对的：一个存档一套记忆，天然隔离，不需要额外管理。
但对我们**不适用**——我们的记忆要跨重启、跨群累积，不能绑在某条消息上（见第六节）。

## 三、存储与"检索"

### 3.1 存储结构

```
chat[i].dataTable      → 那条消息当时的表格快照
chat[i].hash_sheets    → 表格的哈希引用
BASE.templates         → 用户定义的模板（schema 来源）
BASE.sheetsData.context → 当前生效的 sheet 实例
```

一个 sheet 的字段（从 `getTablePromptByPiece` 的 customParts 反推）：

| 字段 | 作用 |
|---|---|
| `title` | 表名 |
| `node` | 列定义（告诉模型有哪些列、每列是什么） |
| `headers` | 列名行 |
| `rows` | 数据行 |
| `editRules` | 编辑规则（怎么增删改，写进 prompt 教模型） |
| `enable` | 是否启用 |
| `sendToContext` | 是否注入 prompt（可以建了表但不注入） |

`enable` 和 `sendToContext` 分开这件事很实用：**表可以留着做记录，但不占 prompt**。

### 3.2 它没有检索

这是最容易被忽略、但最关键的一点：**它不做任何相关性筛选**。

`getTablePrompt()` 把**所有** `enable && sendToContext` 的表的**全部行**拼成一段文本，整块塞进 prompt。

为什么可行：
1. RP 的记忆量小（几张表 × 十几行，通常 2000 字以内）
2. 用户会主动删过时的行（有表格 UI）
3. 模型自己能从表里找到相关的那行

**为什么我们不能照抄**：我们的记忆是自动攒的，200 条上限，全量注入塞不进 8000 字预算，
而且模型面对 200 条无关信息会分心。所以**检索这一层我们必须自己做**——
这正是我们方案里 2-gram + 相关性门槛 + TTL 要解决的问题。

## 四、关键实现方案（这部分最值得细看）

### 4.1 操作排序：update → insert → delete（倒序）

```js
const priority = { update: 0, insert: 1, delete: 2 }
return actions.sort((a, b) =>
  (priority[a.type] === 2 && priority[b.type] === 2)
    ? (b.action.rowIndex - a.action.rowIndex)   // delete 按行号倒序
    : (priority[a.type] - priority[b.type]))
```

为什么这个顺序是对的：

- **update 先做**：改的是已有行，行号还没变
- **insert 次之**：插入会让后面的行号整体后移，但此时 update 已经做完
- **delete 最后，且从后往前删**：先删第 3 行再删第 1 行，索引不会错位；
  反过来先删第 1 行，第 3 行就变成第 2 行了

**这是行号索引操作的经典陷阱。** 我们现在用 id 不用行号，看起来免疫，
但如果三期做「摘要合并」（把 10 条压成 1 条），就是一次批量删除 —— 同样要处理这个问题。

### 4.2 越界自动降级：update 越界转 insert

```js
const rowIndex = action.rowIndex ? parseInt(action.rowIndex) : 0
if (rowIndex >= sheet.getRowCount() - 1) {
  return executeAction({ ...EditAction, type: 'insert' }, sheets)
}
```

模型给的行号超了（它记错了表有几行），不报错，直接当成"追加一行"。

**这个宽容度很关键**：模型算行号本来就不准，一次报错就等于这条记忆丢了。
宁可插到末尾，也不要丢。

### 4.3 幂等：同一段操作不重复执行

```js
function isTableEditStrChanged(chat, matches) {
  if (chat.tableEditMatches != null && chat.tableEditMatches.join('') === matches.join('')) {
    return false   // 内容没变，不再执行
  }
  chat.tableEditMatches = matches
  return true
}
```

触发点有三个：`onMessageReceived`（新回复）、`onMessageEdited`（用户编辑消息）、
`onMessageSwiped`（重新生成）。同一段 `<tableEdit>` 可能被解析多次，
不幂等的话「插入一行」会变成「插入三行」。

**这对我们有直接意义**：我们的记忆是"解析回复 → 落库"。
如果用户编辑了那条回复、或者协议端重投消息，就会重复落库。
现在靠 `addFact` 的完全包含去重挡着，但那只挡完全相同的文本。

### 4.4 操作记录写回消息（作为 HTML 注释）

```js
getTableEditActionsStr() {
  return "\n<!--\n" + actions + "\n-->\n"
}
```

解析完的操作会作为 HTML 注释放回消息里。这样：
- 表格状态可以从聊天记录**重建**，不依赖额外存储
- 用户能看到"AI 到底改了表里的什么"

### 4.5 两个开关分离：AI 能读 ≠ AI 能写

```
isAiReadTable   → 是否把表注入 prompt
isAiWriteTable  → 是否解析回复里的编辑指令
```

四种组合都有意义：
- 都开：AI 自由读写（默认）
- 只读：AI 参考记忆但不许改（**防止乱记**）
- 只写：AI 记录但不看（分步模式的上半段）
- 都关：纯手动管理

**这个拆分我们用得上。** 现在我们的记忆只有一个 `memory.enable`，
用户想「记录但别在回复里提」或者「读但别写」都做不到。

### 4.6 注入深度 `deep`

```js
if (deep === 0) chat.push({ role, content: prompt })      // 追加到最后
else chat.splice(-deep, 0, { role, content: prompt })       // 插到倒数第 deep 条之前
```

配合 `injection_mode`（注入成 `system` / `user` / `assistant`），
用户能控制记忆"离当前对话多远、以什么身份出现"。

我们现在是固定塞进 user 消息里。**没有"注入多深"这个概念** ——
所有记忆和当前消息挤在一起，模型分不清"这是长期印象"还是"这是刚才说的"。

### 4.7 宏引用：`{{GET::表名:B2}}`

```
角色卡里写：我的名字是 {{GET::角色:name}}
→ 渲染时取出表格里那一格的值
```

这是个很强的能力：**单条记忆可以被精确引用**，而不只是"整块注入等模型自己找"。
RP 场景里用来把角色的固定属性嵌进世界书。

对我们：我们的 preset system 里如果要写「你叫小张，24 岁」，
现在只能把值硬编码在 yaml 里。有宏的话可以 `{{GET::人设:name}}`，
改人设表格就自动生效。

### 4.8 失败不阻塞

```js
try { ... } catch (error) {
  EDITOR.error(`记忆插件：表格数据注入失败\n原因：`, error.message, error)
}
```

注入和解析失败都只记日志，不往上抛。记忆功能坏了，聊天照常进行。

这条我们现在也是这么做的（`guard` / `gate` 判定失败一律放行），思路一致。

## 五、三方对比：三种不同的取舍

同一个问题（"AI 怎么记住事"），三个项目给了三个答案：

| 维度 | st-memory（表格） | LivingMemory（检索） | 我们（中间路线） |
|---|---|---|---|
| **谁决定记什么** | 用户定 schema | 模型自由总结 | 模型自由总结（要改） |
| **怎么防记歪** | 列定义约束输入 | 事后打分/衰减/冲突消解 | 事后过滤（相关性门槛） |
| **怎么找回来** | 全量注入，模型自己找 | 四路检索融合 | 2-gram + 门槛 |
| **适合的记忆量** | 几十行 | 万级 | 几百条 |
| **记忆谁维护** | 用户（有 UI） | 模型自动 | 模型自动 |
| **数据在哪** | 聊天记录 | SQLite | 独立 JSON |
| **装它的门槛** | 无 | 要配 Embedding Provider | 无 |

**关键洞察**：

> 记忆系统的设计，本质上是在回答「谁对记忆质量负责」。
> 表格方案让用户负责（所以敢全量注入）；检索方案让模型负责（所以要一堆补救机制）；
> 我们现在让模型负责，但既没有表格的 schema 约束，也没有检索方案的事后补救 —— **两头不靠**。

## 六、可借鉴点：适用场景与取舍

按「该不该抄」排序。

### ✅ 值得抄 1：用 schema 约束「记什么」

| | |
|---|---|
| **它怎么做** | 用户定义表格的列，模型按列填 |
| **我们怎么用** | 在记忆契约里给**可选的结构化字段**（`subject` / `predicate` / `type`），并在 prompt 里列出「本群常记的几类」，而不是让模型自由发挥 |
| **适用场景** | 群聊里稳定的信息类型其实就几类：成员身份、群约定、事件、偏好。列出这几类，比「什么值得记」这种开放问题好答 |
| **取舍** | 列定义写进 prompt 会增加字数（约 100 字）；太细会限制模型发现新的记忆类型。做法是**给建议不给限制**：「优先记这几类，其他也可以」 |
| **落在哪期** | 一期（和 `subject/predicate` 一起） |

**这是最有价值的一条。** 我们现在的记忆质量问题是"记了太多没用的"，
根因是契约里 `memory` 只说"值得长期记住的事"，模型只能自己猜标准。

### ✅ 值得抄 2：操作式协议（增/改/删，而非整块快照）

| | |
|---|---|
| **它怎么做** | 模型输出 `insertRow(0, {...})`，插件逐条执行 |
| **我们怎么用** | 记忆契约从 `memory: [...]` 扩展成 `memoryOps: [{op:'add'|'update'|'delete', ...}]` |
| **适用场景** | 需要修正旧记忆时。现在模型没法说「把张三的职业改成腾讯」，只能再加一条，然后靠冲突消解猜 |
| **取舍** | 协议复杂度上升，小模型更容易输出错格式。**必须保留纯 `memory: [...]` 作为兼容路径**，解析失败就退回。排序规则（update→insert→delete 倒序）要照抄，否则批量删除会错位 |
| **落在哪期** | 三期（等 `subject/predicate` 稳定后，才有东西可以"update"） |

### ✅ 值得抄 3：读写开关分离

| | |
|---|---|
| **它怎么做** | `isAiReadTable` / `isAiWriteTable` 两个独立开关 |
| **我们怎么用** | `memory.inject`（是否注入）+ `memory.write`（是否记录），替代现在的单一 `enable` |
| **适用场景** | 用户想「先观察一段时间它在记什么，不管它」；或者「记忆满了，先只读不写」 |
| **取舍** | 配置项 +2，锅巴面板要加。但这是**零风险**的改动，只是把现有逻辑拆开 |
| **落在哪期** | 一期（顺手做，几乎不加代码） |

### ✅ 值得抄 4：幂等保护

| | |
|---|---|
| **它怎么做** | 记住上次解析的原文，一样就跳过 |
| **我们怎么用** | 记忆落库时带一个「来源消息 id + 内容哈希」，重复的不再处理 |
| **适用场景** | 消息被编辑、协议端重投、swipe 重生成 —— 我们已经有 dedup 挡重投，但挡不住"编辑后重新解析" |
| **取舍** | 要在 `memory.json` 里多存一个哈希（每条约 20 字符）。或者更省：只在内存里记最近 20 条的哈希 |
| **落在哪期** | 二期（和 TTL 字段一起加） |

### ⚠️ 可抄但要改造 5：注入深度

| | |
|---|---|
| **它怎么做** | `deep` 参数控制插到倒数第几条之前 |
| **我们怎么用** | 记忆不要和当前消息混在同一条 user 消息里，而是**单独一条**（可以指定 role 和位置） |
| **适用场景** | 让模型区分「长期印象」和「刚才说的话」。现在混在一起，模型容易把记忆当成刚才的对话内容 |
| **取舍** | 我们的 `fitBudget` 是按"一条 user 消息"设计的，拆成多条要改预算逻辑。而且部分中转站对多条 system 消息支持不好 |
| **落在哪期** | 二期 |

### ⚠️ 可抄但要改造 6：宏引用

| | |
|---|---|
| **它怎么做** | `{{GET::表名:B2}}` 在任意 prompt 里取单元格 |
| **我们怎么用** | 人设 yaml 里支持 `{{memory:subject}}`，取该成员最近的一条事实 |
| **适用场景** | 人设想写「你认识群里的 {{alice}}」，自动填成具体的人 |
| **取舍** | 需要稳定的 `subject` 才有意义（依赖三期）。而且宏求值失败时要能优雅降级（它的做法是返回红色错误文本，我们得返回原始占位符） |
| **落在哪期** | 三期 |

### ❌ 不抄

| 它的做法 | 为什么不抄 |
|---|---|
| 全量注入 | 我们记忆会涨到 200 条，8000 字预算装不下；模型面对无关信息会分心 |
| 记忆存在聊天记录里 | 我们要跨重启、跨群累积，不能绑在某条消息上 |
| 表格 UI（增删改单元格） | 有锅巴面板；而且群聊场景没人愿意手填表 |
| 用户手工维护记忆 | 群友不会为了机器人维护表格。这是 RP 场景（单人、有代入感）和群聊场景的根本差异 |
| 两步模式（主 API 对话 + 副 API 整理表） | 我们已有类似机制（`gate` / `guard.judgeModel` 用便宜模型做判定），不需要再引入一套 |
| `parseArgs` 那种手写词法分析 | 我们用 JSON，不需要解析函数调用语法 |

## 七、对我们方案的修订建议

参考完这个项目，方案要动三处：

### 7.1 记忆契约要"给建议"，不只是"给格式"

现在（`models/replyParser.js`）的契约只说「memory 放值得长期记住的事」，太开放。

改成（一期）：

```
- memory 优先记录这几类（没有就不用记）：
  · 成员的身份/职业/所在地
  · 群里的约定与规矩
  · 发生过的事件（带时间）
  · 某人的明显偏好
- 除此之外确实重要的也可以记，但不要记寒暄、情绪、玩笑话。
```

**不是**列出固定列（那会限制模型），而是给几个锚点。
这比现在的「只放以后还用得上的信息」具体得多，而字数只多两行。

### 7.2 `memory.enable` 拆成 `inject` / `write`

零风险，一期顺手做。

### 7.3 幂等要在二期补上

现在 `addFact` 的去重是「完全包含」，挡不住「编辑消息后重新解析」。
二期的 `addFact` 加 `sourceHash` 参数，同一 hash 不重复落库。

## 八、一句话总结

AstrBot 教我们**怎么在大数据量下检索**，这个项目教我们**怎么让模型少犯错**。

后者对我们的价值更大，因为我们的痛点不在"找不到"，而在"记了一堆不该记的"。

它给出的答案是：**别让模型自由发挥，给它一个结构**。
这个思路不需要向量库、不需要图数据库、不需要额外依赖 ——
只需要在契约里多写两行，在一期就能落地。
